1. The big picture

Everything runs on the tester's own machine. The tester uses a web page served by a small local server; that server drives a real Chromium browser (Playwright) which opens AMP pages as each user, using the tokens the tester pasted.

Tester UILocal serverBrowser automationAMPFiles
No LLM, no cloud service. The only network traffic is between the tester's machine and the AMP environment being tested.

2. End-to-end flow

What happens from npm start to the report. Steps 5–9 are one run (executeRun in src/run.ts).

  1. Start the tool. npm start launches the local server on 127.0.0.1:4545 and opens the tester page.
    src/server/index.ts · src/server/ui.html
  2. Environment. Tester enters the client's base URL, e.g. https://itbydesign.sb.amp.vg. Production URLs are refused unless explicitly allowed.
    ui.html step 1 → server environmentFrom() → safety/gate.ts assertSafeEnvironment()
  3. Rulebook. Tester picks a saved file or uploads one. The server parses it into rules; its user-type columns become the token rows.
    POST /api/rulebooks/parse → rulebook/parse.ts parseRulebook() → rulebookFromRows()
  4. Tokens. Tester pastes the jwt cookie for the users to test (rows auto-tick) and clicks Check tokens.
    POST /api/tokens/check → sessions/validate.ts validateToken()
  5. Plan. Which pages × which users. Users without a jwt are skipped.
    run.ts planRun() · server setupFrom()
  6. ① Token check. Each token is sent to AMP's getpermissiondataforuser; AMP says who it is. Invalid token → run stops.
    run.ts → sessions/validate.ts
  7. ② Menu read. AMP's main page is fetched as each user; the embedded var navigation = [...] gives that user's menu links.
    probe/menu.ts fetchMenu() · extractNavigation() · collectMenuLinks()
  8. ③ Reference run (if Site Admin tokens given). Site Admin opens every page first; the tool records what each page looks like when it really opens (its fingerprint).
    run.ts probeAll() → probe/browser.ts → verdict/fingerprint.ts buildFingerprints()
  9. ④ Each user. A fresh Chromium with that user's cookies opens every page, collects evidence and a screenshot; evidence + fingerprint → page state → verdict.
    probe/browser.ts probe() → verdict/state.ts accessState() → verdict/compare.ts pageVerdict()
  10. ⑤ Report. results.json, results.csv, report.html (+ screenshots). The tester page shows the summary and an Open report button; tokens are cleared from memory.
    report/write.ts writeReports()

3. Rulebook → Playwright: where each piece goes

The rulebook file

page,name,site_admin,super_admin,normal_user
https://itbydesign.sb.amp.vg/#intel/account,Account,Yes,Yes,No
  • page column (also url, route): which page.
  • every other column: a user type (except name, notes and similar).
  • Values Yes/No; empty = not specified.

After parsing (in memory)

{
  route:    "intel/account",
  label:    "Account",
  expected: { site_admin: "Yes",
              super_admin: "Yes",
              normal_user: "No" }
}

Only the part after # is kept. The domain in the sheet is ignored; the base URL from step 1 is used.

The browser only ever receives the route. The Yes/No values are never sent anywhere; they are used only at the end to compare with what actually happened.

4. How the jwt is used

WhereHow the token is sentWhyCode
Token checkCookie jwt, plus a tool-generated value sent as both cookie and header X-CSRF-Token, POST /services/api.ashx?func=getpermissiondataforuserConfirm the token is live and see who it belongs to (name, persona, company/org, Site Admin?)sessions/validate.ts
Menu readSame cookies, GET /AMP builds this user's menu into the main pageprobe/menu.ts
Page checkscontext.addCookies() puts the jwt (and a generated X-CSRF-Token) into a fresh Chromium; AMP's own page JavaScript then sends them on every requestThe browser is that user for AMP; AMP decides page access from the jwt's user and rolesprobe/browser.ts open()
Same page, same browser code, different jwt → possibly different result. That difference is exactly what is being tested.

Lifetime of a token

  • Pasted in the tester page → sent to the local server (127.0.0.1 only) → kept in memory for that run.
  • Never written to disk, never stored in the browser (localStorage keeps only URLs and labels), masked as eyJhb…x9Q in every log and report.
  • Cleared from memory when the run ends (creds.clear() in server/index.ts).
  • A refresh of the tester page empties the token fields; paste again for the next run.

5. How one page is judged

For each page and each user, BrowserProbe.probe() sets location.hash to the route, waits for the network to go quiet, then records:

EvidenceWhere it comes fromWhat it tells us
Final URLpage.url()Ended on /login / /sessionexpired (bad token) or /noaccess (blocked)?
Page request status + redirectPlaywright response / request events for /<route>302 → /noaccess, 404, 5xx
No-access markerDOM: .error-text-2 (AMP's no-access page)Blocked, even when HTTP said 200
Page elementsDOM: visible element ids and headingsCompared with the fingerprint → did the real page render?
API callsResponses from /api/<Func> and /services/api.ashxPage opened but its data calls answered "no access" → opens empty
Blocked requestsSafety gate decisionsWrite calls the page tried to make (never sent)
Page errorsPlaywright pageerrorJavaScript crashed
Screenshotpage.screenshot()Human-checkable proof

The fingerprint (why a 200 isn't trusted on its own)

A page can return 200 and still show nothing useful. So the tool learns what each page looks like when it really opens:

  1. Per page, the user who saw the most is the reference (whatever that user type is called — Super Admin on one page, Channel Manager on another). Elements present on most pages (the AMP frame) are ignored; what remains is the page's own content.
  2. With one user type only: each page is compared with that user's own view (the report warns). A visible "no access / permission denied / not authorized" message always counts as blocked.
  3. Another user "opened" a page when at least Match threshold (default 60%) of that page's fingerprint is on their screen.

Code: verdict/fingerprint.ts buildFingerprints(), fingerprintScore(); verdict/state.ts accessState().

Only whether the page opens decides pass/fail. The menu is shown as information and only turns "extra access" into "security gap".

9. Safety rules

Requests the tool makes itself

  • Only to the configured environment's host.
  • GET for pages; POST only to the allow-listed getpermissiondataforuser.
  • Throttled (delay between requests).

RequestGate

Requests AMP's page makes in the browser

  • GET: allowed (loads the page).
  • /api/<Func> and api.ashx: allowed only for read-only names (Get…, Load…, Check……), not hidden writes like GetOrAdd….
  • Any other POST/PUT/DELETE, AI calls (/bridge/ask/ai), third-party tracking, and logout: blocked and logged.

decideBrowserRequest(), applied via context.route()

  • The browser only navigates; it never clicks, types or submits.
  • Production environments are refused unless "production" and "approval" are both ticked. Remote URLs must be HTTPS.
  • One page at a time with a delay (AMP rate-limits and alerts on bursts).
  • Every request, allowed or blocked, is in audit.jsonl with tokens masked.
  • Opening pages still writes AMP's normal usage-tracking rows; prefer test users/companies.

12. Troubleshooting

SymptomCause / fix
Error mentions an old rule (e.g. "missing column type") or a change doesn't showThe server is still running old code. In its terminal: Ctrl+C, then npm start, then refresh the page.
Who is it? shows ✗ / "redirected to /login"Token expired or copied from another site. Log in again on that environment and copy fresh cookies.
Menu read fails: no "var navigation" foundThat environment's main page is not at /; the shell path needs adjusting.
Many Review / Unclear resultsOnly one (low-access) user type tested, or a page renders differently per role. Add a higher-access user type (e.g. Super Admin); lower Match threshold slightly if pages differ a lot per user.
Not found for rulebook pagesRoute doesn't exist on that client's build; check the route (the report lists the client's actual menu links).
